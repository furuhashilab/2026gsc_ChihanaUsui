## 実装した機能（2026年11月時点）

### ゲームの流れ

1. 最初の画面で、目的地までの距離とBGMを選ぶ
2. 現在地を取得し、周辺のランドマークから目的地を選ぶ
3. その場で回転し、音が最も大きくなる向きを確かめる（キャリブレーション）
4. 音を頼りに歩く
5. 到着またはギブアップで結果を表示し、記録を保存する

### 目的地の設定

- 距離の選択：近所（約15分・直線300〜500m）、ちょっと遠く（約30分・直線700〜1000m）、長く歩く（約1時間・直線1500〜2000m）、カスタム（100〜3000m）。時間は、歩行速度を分速80m、音を頼りに探すことで実際の歩行距離が直線距離の約2倍になると仮定した目安である
- OpenStreetMapのデータ（Overpass API）から、公園、遊び場、神社、寺院、教会、祠、像・アート作品、記念碑、噴水、眺望地点を検索し、選んだ距離の範囲からランダムに1か所を選ぶ。立入禁止の場所は除外する
- 候補がない場合や通信できない場合は、ランダムな地点を目的地とする
- 目的地の名前はゲーム中は伏せ、結果画面で表示する

### キャリブレーション

- コンパスの向きと目的地の方角の差に応じて音量が変わり、目的地の方向を向くと最大になる
- 時間制限は設けず、プレイヤーが「この向きに出発」を押して歩き始める
- コンパスが使えない場合は待機し、iPhone／Androidそれぞれの許可方法を表示する

### 歩行中の音

- BGMをループ再生し、距離に応じて音量とこもり具合（ローパスフィルター）を変える。遠いほど小さく、こもった音になる
- 残り50mで近距離モードに切り替わる。合図の音が鳴り、音量の変化が大きくなり、はっきりした音になる（GPSのぶれによる切り替わりの繰り返しを防ぐため、60mを超えると通常モードに戻る）
- 向きの強調：歩いている方向（GPSから得られる進行方向。得られないときは直近4m以上の移動から計算）と、目的地の方角を比べる。目的地の方向（約45度以内）に歩き出した瞬間に一度だけ音を大きく明るくし、離れる方向（約120度以上）に歩き出した瞬間に一度だけ小さくこもった音にする。その後、約10秒かけて元の音に戻す。立ち止まると判定をリセットし、再び歩き出したときにもう一度反応する。GPSの精度が±25mより粗いときは判定しない
- 正しい向きの合図：約10秒前の位置と比べて、8m以上歩き、かつおおむね目的地の方向に進んでいれば、小さく「ピピッ」と鳴らす。BGMの音量に関係なく一定の小さな音量で鳴らし、間隔は10秒以上空ける
- 片耳イヤホンで使えるよう、すべての音をモノラルで再生する。立体音響は使用しない
- GPSのぶれを抑えるため、距離を指数平滑化（直前の値と新しい値を一定の割合で混ぜて滑らかにする処理）してから音に反映する
- 到着判定は、目的地から15m以内（公園など面積のある場所は中心から30m以内）とする
- 歩行中の画面には距離を表示しない

### BGM

- OtoLogicの4曲と合成音から選べる
- 選ぶときに、冒頭20秒を試聴できる

### ヒント・一時停止

- ヒント1：キャリブレーションのやり直し
- ヒント2：レーダー（目的地を中心とした距離の目安と、30秒前より近づいたかどうかを表示する。方向は表示しない）
- ヒント3：大まかな方角（8方位）
- ギブアップ：ゲームを終了し、目的地を地図で表示する
- 一時停止：音と時間の計測を止める。一時停止中の移動は、歩いた距離に含めない

### 結果と記録

- 結果画面に、目的地の名前、かかった時間、歩いた距離、直線距離、ヒント使用回数、地図（スタート、目的地、歩いた道のり）を表示する。距離の設定、直線効率（直線距離÷歩いた距離）、一時停止、BGMは「くわしい記録」に折りたたんで表示する。ヒントの種類ごとの回数や強調の回数は、CSVに記録する
- 記録は端末のブラウザ内（localStorage）に保存し、「これまでの記録」で一覧と詳細を確認できる。CSVでの書き出しと全削除に対応する

### プライバシー

- 位置情報と記録は端末内だけで処理・保存し、開発者を含む外部には送信しない
- 目的地の検索時のみ、約100m単位にぼかした現在地をOverpass APIに送信する

### その他

- 音のテスト（室内用）：スライダーで距離を変え、歩かずに音の変化を確かめられる
- 開発者表示：GPSの精度、距離、方位などの内部の値を表示する
- 画面が自動で消えないようにする（対応している端末のみ）
- 困ったときは（help.html）：許可の設定、GPS、音、スマホの持ち方、記録、プライバシーなどをQ＆A形式でまとめたページ。アプリ内のエラー表示からも、該当する項目へ直接移動できる
- 初回の許可の案内：ブラウザの許可画面が出る前に、何を許可するのかと位置情報の使い方を説明する画面を表示する（初回と、許可が拒否された後のみ）

### 未実装・保留

- 振動：iPhoneのブラウザでは使えないため保留。必要に応じてオプションとして追加する
- 距離に応じて間隔が変わる音：焦りを感じさせる可能性があるため停止している（プログラム内には残している）
- 画面が消えると、音とGPSが止まる（Webアプリの制約）

## Claim（主張）

出発時のみのコンパスキャリブレーションと、歩行中は距離に応じた音量変化のみを用いることで、画面を見ず・両耳を塞がずに安全に、かつゲームとして楽しみながらランダムな目的地に到達できる。

---

## 概要

既存の位置情報ゲームは、地図が画面上に表示され、それに従って歩行する仕組みのものが大半で、歩行中の視覚的な注意をアプリに向けさせる設計になっている。歩行中の「ながらスマホ」は事故の原因となり危険である。また、「風景を見ながら歩くのを楽しむ」という点に重点を置くゲームは少ない。

本研究では、完全ランダムに生成した目的地に対し、出発地点でのみ方向をコンパスキャリブレーションし、歩行中は目的地までの距離に応じた音量変化のみで接近を伝える、音のみのナビゲーションシステムを開発する。これにより、画面を見ず、かつ両耳を塞がない（モノラル・片耳イヤホン対応）安全な散歩体験の実現を目指す。

---

## Introduction

### 背景

- **地図表示型ナビゲーション／記録アプリ**（例：ALKOO by NAVITIME）は、到達圏探索の技術を用いて経由地をランダムに選ぶなど工夫があるが、地図を見ながら歩くことが前提になっている。
- **ランダム目的地型アプリ**（Dokoka, Wherewalk）は、行き先を伏せて発見を楽しませる面白い仕組みを持つが、矢印や地図など視覚情報に依存している。
- **位置情報ゲーム型アプリ**（ポケモンGO、Ingress）は、収集・陣取り等の要素によって非常に強い継続動機を生み出すことに成功しているが、常時画面を確認する必要があり、「ながらスマホ」による事故等が社会問題として指摘されてきた。歩くことをゲームで包む設計は継続には効くが、「風景を楽しみながら歩く」という体験そのものからは距離ができてしまう。
- 音声によるナビゲーション研究は、主に視覚障害者支援の文脈で発展してきた（SWAN, audioGPS, Microsoft Soundscape, NavCog等）。これらは空間化された音（バイノーラルオーディオ）でビーコンを定位し、体の向きを常に音源へ追従させる方式が中心であり、両耳を塞ぐ形になるため屋外歩行時の安全性（周囲の音の聞こえにくさ）に懸念がある。
- アンビエントな音声誘導研究（Hearing the Way Forward, CHI 2023）や、音楽をナビゲーションに統合する研究（Guided by Music）など、「地図を見ない」誘導手法の研究も近年蓄積されつつある。

### 目的

出発時の一度きりの方向キャリブレーションと、歩行中の距離ベース音量フィードバックのみを用いて、画面を見ず・両耳を塞がずに安全に、かつ楽しみながらランダムな目的地に到達できるナビゲーションシステムを開発し、その実用性・安全性・面白さを明らかにすることを目的とする。

### 意義

- 目的地に安全に導く方法は他にもある（立ち止まって画面を確認する、3D音響で正確に方向を示す、等）。本研究では、あえてそうした手段を採らず、出発時一度きりのキャリブレーションと距離のみのフィードバックに絞ることで、安全性とゲームとしての面白さ（自分で方向を探る楽しさ）を両立させる設計を提案する。
- 既存の音声ナビゲーション研究の多くが前提とする「両耳・空間オーディオ」への依存を避け、モノラル・片耳イヤホンでも成立する設計を提示することで、音声ナビゲーション研究に安全性の観点から新しい選択肢を示せる。
- 空間情報系の技術（GPS、方位角計算など）を、位置情報ゲームという体験デザインに応用する実践例を示せる。

## Methods

### システム設計（体験設計）

- **目的地生成**：現在地から一定範囲内で完全ランダムに座標を1点生成
- **出発時キャリブレーション**：その場で一回転し、目的地方向で音量が最大になるように提示
- **歩行中フィードバック**：距離に応じた音量変化のみ（方向情報は使用しない）。対数的マッピングを想定
- **音の種類**：ユーザーが選択可能な音楽・環境音。モノラル前提
- **振動**：距離に応じた間欠パルス（常時振動は発熱・電池消費・煩わしさの観点から避ける）。補助的な位置づけ
- **ヒント**：停滞検知時に段階的な救済（曖昧な距離感 → 大まかな方角 → 地図表示のギブアップモード）
- **事後振り返り**：所要時間、実移動距離／直線距離比、ヒント使用回数を記録・表示

### 使用ツール（想定）

実装はAIによるプログラミング支援を活用しながら進める想定。実装形態はWebアプリで進める方針とする。
※ブラウザ経由のため、GPSや振動などの機能に一部制限がある場合がある（特にiOS Safari）。実装を進める中で問題が出た場合は、ネイティブアプリ化も検討する。

### 評価計画（想定）

比較実験（他のアプリ・型との対決形式）ではなく、**提案システム単体のフィールドテスト**によって、実用性・安全性・面白さを検証する方針とする。

- 客観指標：到達所要時間、ヒント使用回数、実移動距離／直線距離比、実際に画面を確認した回数・時間（安全性を実測で裏付ける指標）
- 主観指標：満足度、面白さ、認知負荷（作業のしんどさを測るアンケート手法の利用を検討）、安全に歩けたと感じたか

## 決めきれてない部分・まだわからない部分

- 目的地生成の範囲（半径）パラメータ
- 評価実験の被験者数・実施期間
- 電子コンパスの精度（磁気干渉によるズレ）への対処方法
- 完全ランダムな目的地生成による安全性リスク（危険な場所・私有地・行き止まり）への対応方針
- Webアプリでのセンサー機能（GPS・振動等）の制限が実装上問題になった場合、ネイティブアプリへの切り替えを検討する
